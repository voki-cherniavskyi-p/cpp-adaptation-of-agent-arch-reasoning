# Практика: AI-агент для проверки и проектирования архитектуры

Мы пройдём весь путь от требований до задач в трекере:

1. **Соберём требования.** Поговорим с тимлидом (его играет AI-агент) и запишем, чего от нас хотят.
2. **Проверим требования на соответствие архитектуре.** С помощью AI сверим требования с текущей архитектурой, ADR и кодом движка.
3. **Соберём своего агента.** Опишем его карточкой, сгенерируем `CLAUDE.md`, проверим ограничения и подключим Asana через MCP, чтобы разложить решение на задачи.

Сценарий: студия **Northwind Studios** и её C++ движок (`engine/`, open-source фреймворк **Oxygine**, подключён как git submodule). Это C++11 движок с OOP-иерархией сущностей от `Actor`, рендерингом OpenGL ES за единственным бэкендом `IVideoDriver` (`VideoDriverGLES20`) и одним потоком update/render.

Тимлид: **Sofia Lindqvist** (`team-lead/`), хочет перевести сущности с иерархии `Actor` на data-oriented ECS.

## Структура репозитория

```
├── engine/                              ← код, который анализирует агент (git submodule: Oxygine)
│   └── oxygine/src/                     ← исходники движка: иерархия Actor/Sprite + GL-рендерер
│
├── data/
│   ├── context/company.md               ← Northwind Studios: бизнес-контекст, боли, ограничения
│   ├── adrs/
│   │   ├── ADR-001-entity-model.md      ← минимальный ADR (намеренно «тонкий»)
│   │   ├── ADR-002-rendering-api.md     ← хорошо структурированный ADR
│   │   └── ADR-003-render-threading.md  ← устаревший ADR про однопоточный рендер
│   └── diagrams/
│       └── current-architecture.mmd     ← текущая архитектура движка (Mermaid)
│
├── skills/                              ← готовые скрипты-инструменты агента, не менять
│   ├── list_adrs/list_adrs.py           ← список всех ADR в JSON
│   ├── read_adr/read_adr.py             ← чтение одного ADR по ID
│   ├── write_adr/write_adr.py           ← проверка и сохранение нового ADR в output/adrs/
│   └── save_diagram/save_diagram.py     ← проверка и сохранение Mermaid-диаграммы в output/diagrams/
│
├── output/
│   ├── adrs/                            ← сюда агент пишет новые ADR
│   └── diagrams/                        ← сюда агент пишет новые диаграммы
│
├── team-lead/
│   └── CLAUDE.md                        ← персонаж: Sofia Lindqvist, миграция на ECS
│
├── .claude/settings.json                ← разрешения Claude Code для проекта
├── CLAUDE.md.template                   ← шаблон нашего агента (шаг 3)
└── README.md
```

Файлы, которые появятся по ходу практики (`requirements.md`, `difference.md`, `agent-card.md`, `CLAUDE.md`, содержимое `output/`), в git не попадают.

## Шаг 0. Подготовка

Нужны Claude Code, Python 3 и git.

```bash
git clone https://github.com/voki-cherniavskyi-p/cpp-adaptation-of-agent-arch-reasoning.git
cd cpp-adaptation-of-agent-arch-reasoning
git submodule update --init                # подтягивает зафиксированный коммит Oxygine в engine/
python3 skills/list_adrs/list_adrs.py      # проверка, что скрипты работают
python3 skills/read_adr/read_adr.py ADR-001
```

Прочитайте `data/context/company.md`, чтобы понять сценарий, и загляните в `engine/oxygine/src/`: иерархия `Actor`/`Sprite` и рендерер (`STDRenderer` → `IVideoDriver`, GLES-бэкенд в `core/gl/`).

В конце попросите записать требования в корень репозитория:

```bash
cd ..

```

```
Прочитай контекст компании в data/context/company.md и все ADR в data/adrs/ (используй скрипты skills/list_adrs и skills/read_adr). Затем прочитай требования тимлида в requirements.md. Сравни требования с текущей архитектурой и принятыми решениями, при необходимости сверься с кодом в engine/. Найди пробелы и противоречия: что требуется, но не поддержано архитектурой; где требования конфликтуют с ADR; какие ADR устарели. Для каждого пункта укажи источник (файл и раздел). ## Шаг 3. Собираем своего агента
```

Разовый промпт из шага 2 придётся каждый раз вспоминать и набирать заново. Сделаем из него повторяемого агента со своими правилами и ограничениями.

### 3.1. Карточка агента

Хороший агент, как и любой продукт, начинается с короткого описания. Создайте `agent-card.md` и ответьте в нём на 8 вопросов:

| Поле | Вопрос | Пример для нашего агента |
|---|---|---|
| **Цель** | Зачем агент нужен? | Предлагать архитектурные решения под требования тимлида и документировать выбранное решение. «Найти расхождения» — это шаг workflow, а не цель. |
| **Входные данные** | Что он получает на вход? | `requirements.md`, `data/context/company.md`, `data/adrs/`, `data/diagrams/`, `engine/` |
| **Выход** | Что отдаёт? | Анализ (таблица пробелов и конфликтов со ссылками на источники), 2–3 варианта со стоимостью, рисками и сроками; после выбора варианта диаграмма и ADR |
| **Инструменты** | Чем пользуется *сам агент*? | `list_adrs`, `read_adr`, `write_adr`, `save_diagram`, чтение и поиск по коду. «Cursor» или «VS Code» — неправильный ответ |
| **Триггеры** | Когда запускается? | Фраза «проанализируй архитектуру» |
| **Среда** | Где работает? | Claude Code локально, в корне репозитория. Читать можно всё, писать только в `output/` |
| **Защитные механизмы** | Чего ему нельзя? | См. обязательные правила ниже |
| **Human-in-the-loop** | Где решает человек? | Выбор варианта, разрешение на запись ADR, конфликты в требованиях, всё, что уходит на ревью коллегам |

Загляните в `.claude/settings.json`: без подтверждения разрешены `python3` и `git *`, а это в том числе `git push`. Поэтому ограничения нужно прописать явно.

**Обязательные защитные механизмы:**

- `write_adr` вызывается, только если в сообщении человека есть «write adr», «save adr» или «publish»;
- `save_diagram` вызывается только после того, как человек выбрал вариант;
- не изменять `engine/`, `data/` и существующие ADR. Если решение меняется, пишется новый ADR, который заменяет старый;
- никаких `git commit` и `git push`;
- каждое утверждение со ссылкой на файл. Если источника нет, так и написать, а не выдумывать;
- агент анализирует и документирует, но код не пишет.

### 3.2. Генерируем `CLAUDE.md`

Попросите Claude собрать агента по карточке и шаблону:

```
Возьми agent-card.md в качестве описания агента и сделай на основании него готовый файл CLAUDE.md по шаблону CLAUDE.md.template
```

Проверьте, что в `CLAUDE.md` не осталось `[TODO]`, есть оба обязательных правила (`write_adr` и `save_diagram`), а workflow останавливается после вариантов и ждёт выбора человека.

### 3.3. Запускаем и проверяем агента

`CLAUDE.md` подхватывается при старте сессии, поэтому перезапустите Claude Code в корне (или выполните `/clear`) и отправьте фразу-триггер:

```
проанализируй архитектуру
```

Агент должен:

- прочитать `company.md`, все 3 ADR и код движка;
- выдать таблицу пробелов и конфликтов со ссылками на источники;
- предложить 2–3 варианта со стоимостью, рисками и сроками;
- **остановиться и ждать**, не вызывая `write_adr` и `save_diagram`.

Сравните результат с ручным анализом из шага 2:

```
Сравни свой анализ с difference.md: что совпало, что ты пропустил и что нашёл нового. Ответ дай в чате, файлы не меняй.
```

Если агент что-то пропустил, это повод дописать в `CLAUDE.md`, куда ему смотреть.

Проверьте ограничение на запись ADR:

```
Выглядит отлично, одобряю. Оформляй ADR.
```

Агент **не должен** записать ADR: вариант не выбран, а «одобряю» не является разрешением. Затем доведите поток до конца:

```
Берём рекомендованный вариант. write adr
```

Диаграмма должна появиться в `output/diagrams/`, ADR в `output/adrs/`. Диаграммы в формате Mermaid (`.mmd`) можно открыть прямо в IDE.

### 3.4. Подключаем Asana через MCP

Решение ещё не работа: его нужно разбить на задачи и раздать команде. Подключим агенту Asana через MCP.

1. Подключите Asana. Если вы входите в Claude Code через аккаунт claude.ai, достаточно подключить коннектор Asana в настройках claude.ai, и он появится в Claude Code.
2. Проверьте подключение командой `/mcp`.
3. Проверьте, что агент видит Asana:

```
дай заголовок последней задачи, которую я закрыл в асане
```

Создание задач в Asana — действие наружу, его увидит вся команда. Поэтому сначала план, потом подтверждение человека. Для экспериментов используйте тестовый проект, а не рабочий.

## Советы

- Анализ агента должен опираться на боли из `data/context/company.md`, особенно на иерархию `Actor`, промахи кэша в цикле update и сроки консольного порта.
- Агент должен рассуждать о том, что реально делает код в `engine/oxygine/src/`, а не только о том, что написано в документах.
- Правило записи ADR — самое важное ограничение. Проверьте, что агент **не** вызывает `write_adr` на «выглядит хорошо» или «одобряю».
- Если агент пропускает шаг, добавьте в workflow явный порядок: «не переходи к шагу N, пока не завершён шаг N−1».
- Ловушка ADR-003: модель сущностей и рендерер нельзя мигрировать одновременно, а ADR-002 требует переделать рендер-бэкенд до консольного порта. Хороший агент показывает этот конфликт по срокам и оставляет решение человеку.
- Для Cursor или Windsurf: то же содержимое `CLAUDE.md` сохраните в `.cursor/rules/architecture-agent.mdc` или `.windsurfrules`. Для тимлида откройте `team-lead/` как отдельный корень рабочей области.
